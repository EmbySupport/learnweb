    Measuring the actual streaming delivery path

    A streaming-capacity measurement must use the intended endpoints, direction, protocol and workload, retaining interval and receiver-side progress before testing the actual Emby presentation.

    Start with the path whose result matters: the Emby sender, the actual viewing device or a suitable receiver beside it, and the direction in which the media travels.

    A test to another internet endpoint can be useful context, but it measures another path.

    Describe the question before running a test

    A useful observation record includes:

    Input Why it belongs with the result
    Sender and receiver Selects the path
    Data direction Identifies which upload/download resources are used
    Address family and endpoint Retains IPv4/IPv6 and proxy/VPN differences
    Protocol and connection count Distinguishes one-flow and aggregate behavior
    Duration and interval results Exposes transient deficits
    Other active traffic Records the sharing context

    For remote playback, data normally leaves the Emby household toward the viewer. A measurement in the opposite direction can miss that uplink constraint.

    A controlled receiver test has its own service

    iperf3 uses an explicitly established client/server measurement arrangement. It does not turn the Emby application port into an iperf receiver.

    An original illustrative invocation is:

    iperf3 -c receiver.example.net -R -t 20 -i 1

    The example assumes an appropriate measurement receiver has been arranged. The reserved hostname is not a real target, and the command was not run.

    The reverse flag makes data travel from the measurement server to the invoking client. That can represent a media-server-to-viewer direction when those roles are deliberately placed on the intended path.

    A normal client-to-server test has another direction. Do not label one “upload” without identifying whose side is being described.

    Preserve receiver-side intervals

    Consider original useful payload results over two-second intervals:

    {
  "secondsPerInterval": 2,
  "receivedBytes": [10000000, 1000000, 10000000]
}

    The interval rates are forty, four and forty Mbit/s. The whole-test average is twenty-eight.

    A twenty-Mbit/s presentation can fit that average yet experience a sixteen-Mbit/s deficit during the slow interval. Its current usable reserve determines whether that interval can be tolerated.

    Sender and receiver reports can differ in what reached the observation boundary. Use the appropriate receiver-side useful data for a delivery claim.

    Translate a slow interval into required reserve

    For the separate stated twenty-Mbit/s presentation, the four-Mbit/s interval has a sixteen-Mbit/s deficit. Over two seconds, it consumes thirty-two Mbit of existing usable reserve: four decimal MB.

    A player with only sixteen Mbit available at that interval’s start can absorb one second under a constant within-interval rate assumption. A forty-Mbit reserve can absorb two and a half seconds, leaving eight after this two-second interval.

    Those are conditional arithmetic results, not a fixed recommended buffer size. Real transfers arrive in bursts, and received bytes need their media/container/decoder context before they become usable presentation reserve.

    The example gives an interpretable question for a test: did the observed deficit exceed the reserve actually available at that point? The twenty-eight-Mbit/s whole-test average cannot answer that chronological question alone.

    Change one path input for an informative comparison

    A wired receiver near the viewing location can help separate one wireless segment from the rest of the route. Comparing local and remote delivery can identify an internet-path constraint.

    A different IPv4/IPv6 result, tunnel selection or proxy path changes the question too. Retain those endpoint inputs rather than treating every result as one universal property of “the network.”

    Repeated measurements can reveal time-dependent contention. They still describe their measured workload and interval, not every future household condition.

    Preserve what a changed result can attribute

    Suppose the same original sender obtains eighty Mbit/s at a wired receiver near the TV, while that TV location’s wireless path has repeated low intervals. That comparison supports examining the changed wireless segment. It does not by itself identify signal, contention, backhaul or driver behavior as the cause.

    A local result and a remote result also change more than distance: they can change endpoint family, gateways, upload capacity and proxy/tunnel use. An attribution needs those differences stated.

    A repeatable test record should therefore keep both the controlled change and the other conditions that remained comparable. That makes a useful hypothesis different from assuming any faster alternative proved one particular device was faulty.

    Then test the actual presentation

    A synthetic transfer omits media preparation, container/playlist requests, encryption/application behavior and client decoding/rendering work.

    A real Emby presentation needs its playback mode, selected media rate, server progress and client reserve observed alongside network delivery. A server failing to produce data is different from a path failing to carry already available data.

    Emby’s remote bitrate controls express demand policy; they are not a throughput measurement. Transcode speed supplies another potential production limit.
