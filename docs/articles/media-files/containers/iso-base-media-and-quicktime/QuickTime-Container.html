    QuickTime: MOV Container

    QuickTime MOV stores timed media and presentation information in an atom-based container that predates the ISO base media file format.

    A phone recording can appear portrait even when its stored picture raster is landscape. A production export can be enormous while a phone file with the same MOV extension is small. These observations make sense once QuickTime MOV is read as a presentation structure around media, rather than one codec.

    The format uses atoms, each identifying a kind of data and its size. Movie descriptions contain track and timing information; media-data atoms contain the encoded samples. This design was the basis for ISO base media formats, although their file types and conventions remain distinct.

    Sample timing and track edit lists

    A track describes its media type and sample representation. Sample tables identify encoded samples, how long they last, and where they live. The reader finds the bytes and hands them to the appropriate decoder.

    A movie can also use an edit list to relate media time to presentation time. A track may begin after an initial empty interval, or present a range beginning partway through its stored media. Reading every sample from media time zero need not reproduce the presentation described by those edits.

    Information layer What it changes
    Coded samples The reconstructed pictures or sound
    Sample timing and location When samples belong and where their bytes are read
    Track edits Which media range maps onto the movie timeline
    Display transformation How the reconstructed track is placed or oriented

    These layers can change independently. Copying coded samples preserves one of them, not necessarily the complete presentation.

    The portrait phone example

    Suppose the coded raster is 1920 × 1080 and the track describes a 90-degree display rotation. The decoder reconstructs the landscape raster. Applying the transform gives a portrait arrangement whose displayed dimensions exchange width and height.

    A conversion can bake the rotation into newly encoded pixels, or preserve the raster and transfer appropriate orientation information. Copying only the picture bytes while losing the transform produces a sideways result. That error arises after successful decoding, in how the decoded track is presented.

    An editing master has different data demands

    A MOV can hold ProRes or other production media that spends much more data per second than a compact delivery encode. This serves editing and preservation of production information. The same container can also hold a camera's compressed delivery-like video.

    For an Emby source, inspect the actual codec, data rate, track edits, and orientation. Those properties explain why one MOV is straightforward to deliver while another benefits from a smaller viewing copy. An input that merely needs new packaging follows a different transformation from one whose pictures are resized, rotated into pixels, or newly compressed.

    The movie structure records how the media should be assembled. Following it explains both the sound/picture timing and the visible orientation of the final presentation.
