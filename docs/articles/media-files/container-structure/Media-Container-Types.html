    Types of Media Containers

    Containers make different tradeoffs depending on how media will be stored and delivered. A file that can be opened at any byte position has different needs from a broadcast that a receiver joins halfway through.

    Structural approach Why it is useful Familiar example
    Indexed file Describes stored tracks and their locations for navigation A conventional MP4 file
    Repeating transport packets Allows receivers to find stream descriptions in an ongoing transmission MPEG transport stream
    Clustered or fragmented media Carries media in successive groups instead of depending entirely on one complete final index Matroska clusters or fragmented MP4

    These are structural approaches, not exclusive product categories. A format may support both ordinary file playback and streaming arrangements.

    “A streaming format” needs context

    An ordinary media file can be served over HTTP, especially when the client can request byte ranges. That does not make it the same thing as a live broadcast or an adaptive-streaming presentation.

    Conversely, transport packets can be recorded into a file. Their broadcast-oriented structure remains even though the programme is now on disk.

    When Emby delivers media, the server may use packaging that suits the receiving app rather than send the original file structure unchanged. The playback method tells you more about that session than a label such as “streaming container.”

    For a container choice, consider the actual question: can the target read its tracks, begin promptly, and seek reliably? A format's ability to store a codec or survive an interrupted recording is useful, but neither guarantees compatibility with every player.
