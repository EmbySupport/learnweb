    Container Overhead

    The size of a media file is not simply the sum of its video and audio payloads. The container also needs headers, track descriptions, timestamps, and navigation structures. Those bytes are container overhead.

    Some costs occur once, such as a track description. Others repeat for each packet, group of samples, or fragment.

    Added bytes Purpose
    Track headers and codec configuration Tell the reader what each track contains
    Timing and indexes Synchronize playback and locate seek positions
    Repeated packet headers Identify and delimit media in the stored sequence
    Padding or reserved space Maintain an output layout or allow later changes

    For scale, a standard MPEG-TS packet occupies 188 bytes and has at least a four-byte header. That minimum header alone is about 2.1% of the packet. Adaptation fields, tables, and padding can add more, so 2.1% is not a general total-overhead estimate.

    Why remuxed files differ in size

    Copying the same encoded tracks into another container can produce a different file length without changing their decoded picture or sound. Different indexing, packetization, metadata, and padding account for some of the difference.

    Removing an audio track or an attachment changes the size too, but that is removed content, not improved container efficiency. Compare the track list when assessing a remux.

    For Emby network estimates, distinguish container overhead from HTTP, TCP, IP, and other delivery overhead. The file's overall bitrate includes its container bytes; a network transfer includes additional protocol costs. Neither is a direct measure of compression quality.
