    Packet Timestamps

    The order in which compressed video is read is not always the order in which pictures appear. A picture may depend on a later displayed picture, so the decoder needs that reference first.

    Two timestamps keep those jobs separate:

    • DTS, the decoding timestamp, places data on the decode timeline.
    • PTS, the presentation timestamp, places the decoded result on the display or sound timeline.
    Packet in decode order DTS PTS
    Picture A 0.00 s 0.04 s
    Picture C, a reference for B 0.04 s 0.12 s
    Picture B 0.08 s 0.08 s

    Simplified reordered-video example. The decoder receives A, C, B; the viewer sees A, B, C.

    The timestamps are often stored as integer ticks. Their time base tells you how to convert those ticks to seconds. A container or inspection tool may represent one timeline through durations and offsets rather than store both values explicitly for every packet.

    Why a warning needs interpretation

    A non-monotonic presentation timestamp in decode order can be normal for reordered video. A DTS that moves backward in a stream expecting ordered decode timestamps is a different problem.

    Gaps, incorrect offsets, or discontinuities can affect audio synchronization and seeking through Emby. A media packet is also not necessarily a single displayed frame, and it is not an IP network packet.

    Do not “fix” timestamps by making every number consecutive without understanding the source. That can destroy legitimate reordering or variable timing. Compare the actual times, the selected tracks, and the reported symptom first.
