    Matroska Attachments

    Styled subtitles can look different even when their text is identical. One reason is that the original file supplied a font that the new playback path never receives. Matroska attachments provide a way to bundle supporting files with the media.

    An attachment has a filename, media type, and file contents. It is separate from the timed video, audio, and subtitle tracks: a font file does not have a sequence of presentation timestamps.

    Common attachment Possible use
    TrueType or OpenType font Supplies a typeface requested by styled subtitles
    Cover image Provides artwork associated with the file
    Other supporting resource Stores a file the receiving software may choose to use

    The container can carry a resource without forcing a player to interpret it. A reader may ignore attachments or support only particular uses.

    A font can matter to more than appearance

    A different font changes letter widths and line breaks. That can shift text, alter signs, or make a carefully positioned subtitle harder to read. Having the font attached helps only if the subtitle renderer can use it in the selected playback path.

    When troubleshooting an Emby subtitle difference, check both the subtitle track and the attachment list. A direct playback renderer and a server rendering subtitles into video may receive and handle supporting resources differently. Their results need to be compared on the actual app and server configuration.

    Remuxing can copy picture and sound while dropping attachments. That is a metadata/resource preservation issue rather than loss of the encoded movie. Inspect the output package before concluding that a conversion preserved everything.

    Cover attachments also differ from separately stored library artwork. Their presence does not establish that a library will display them in every artwork role. The source file and the library's metadata choices are distinct layers.
