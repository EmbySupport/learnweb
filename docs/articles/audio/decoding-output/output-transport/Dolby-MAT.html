    Dolby MAT Audio Transport

    The library file says Dolby Digital Plus with Atmos. The receiver says Dolby MAT. Follow one playback session, and those two labels can fit together:

    Point in the session What is present Job performed here
    Library file Dolby Digital Plus with an Atmos presentation Stores the compressed soundtrack
    Emby Server delivery The selected audio track, supplied without conversion Delivers the source presentation to the app
    Player processing Decoded audio with the required spatial information retained Decodes the compressed presentation
    Supported HDMI output A PCM-based Dolby MAT presentation Transports audio and associated Atmos information
    Receiver The received presentation and the configured speaker layout Renders the audio for those speakers

    This example assumes a player with the appropriate decoder and a supported PCM-based Atmos output route. Dolby MAT, Metadata-enhanced Audio Transmission, is the transport in the fourth row. The receiver names what arrived there; the file names what was stored in the first row.

    Read the chain at each boundary

    1. Server to player. Supplying the selected compressed track unchanged leaves decoding to the player. A receiver indication farther downstream cannot establish whether the server changed the audio; check the actual server delivery path for that part of the chain.

    2. Decoder to output. Decoding reconstructs audio, while rendering determines how a channel or object presentation becomes signals for speakers. An object-aware player can decode a compressed Atmos presentation and retain the information needed for downstream rendering. These are separate jobs, which is what makes a decoded Atmos transport useful.

    3. HDMI to receiver. In the PCM-based MAT 2.0 use, the link carries audio together with the associated Atmos metadata. The receiver can use that presentation with its speaker arrangement. It receives more information than an ordinary set of completed 5.1 or 7.1 channel samples.

    4. Receiver to speakers. Detected input information and the selected listening mode answer different questions. The former describes what arrived; an upmixer or other listening mode describes processing after receipt. Read the input-format report when tracing the source-to-receiver path.

    Change one part of the session

    Keep the same source track and server delivery, but select ordinary channel PCM output in the player. The receiver might now receive a completed 7.1 presentation: eight channels that it can play or further process. Those channels describe that particular rendering. They do not carry the original object presentation simply because the connection has room for multichannel PCM.

    Select encoded passthrough instead, where the whole path supports it. The downstream device then performs decoding as well as rendering. The placement of the decoder has changed, while the selected source may stay the same.

    Now change server delivery to an ordinary audio transcode. The app may receive a new channel-based presentation before it makes any output decision. A later MAT-capable output cannot reconstruct spatial information that the earlier conversion omitted.

    These changes explain why “where was it decoded?” is only part of the investigation. Follow what information survived each boundary, and the audible result becomes easier to account for. The audio playback path describes the surrounding stages.

    Why TrueHD playback also uses the MAT name

    MAT originally provided carriage for a variable-rate TrueHD bitstream over the HDMI audio transport arrangement. In that use, the source packs encoded TrueHD data into the transport and the receiving device unpacks and decodes it.

    PCM-based MAT 2.0 extends the possible route by carrying a decoded Atmos presentation with its metadata. The shared MAT name consequently does not locate the decoder by itself: identify the actual use and the source and output information.

    A media inspector examines the stored track. It can correctly identify TrueHD in an MKV even though the receiver describes its transport using MAT. There need not be a stored MAT track in the library file.

    Record the session in terms that can be compared

    For an Emby playback investigation, collect the selected source track, server delivery mode, player output choice, receiver input report, and speaker/rendering configuration. Together they describe a path. Reading just the file label or just the receiver's listening mode leaves several operations unexplained.

    Transport also preserves the compression history of the audio it carries. A decoded lossy source already contains the reconstruction from that lossy encode. Sending it onward without another lossy encoding step preserves that result; it does not turn the source into a lossless recording. A lossless TrueHD source can retain its recovered samples through a supported output path that preserves them.

    The file and receiver labels then have precise roles in the record: one identifies the retained source, and the other identifies the presentation delivered across the audio connection.
