    Storage access from background services

    A background service opens storage through its own credentials and pathname environment, which can differ from an interactive desktop session.

    “I can open the file in Explorer” proves that the interactive process can open it. Emby Server running as a service performs its own open under another process context.

    That context includes identity, group membership, network authentication, mounted paths and sometimes service-specific file-system restrictions. The desktop test can be completely accurate while the service still fails.

    Compare the two access attempts

    Property Interactive desktop Background service
    Identity Logged-in user Configured service identity
    Windows drive mappings This logon session's mappings A separate logon context
    Linux groups Current shell credentials Server process's current credentials
    Mounted tree Desktop or shell view Service namespace and mappings
    Network connection Credentials available to that context Credentials available to the service

    A service configured with the same Windows account name still receives its own logon session. It does not inherit every redirected drive letter created in that account's desktop session.

    A UNC path names the share without that drive-letter dependency. The service still needs appropriate remote credentials and rights. Replacing a letter with a UNC name fixes one possible naming failure, not every access failure.

    Linux service restrictions can change the view

    A Linux service manager can select the service's user, groups and execution environment. It can also establish restricted mount arrangements or make selected paths read-only or inaccessible.

    A root-owned host directory being visible in an administrator's shell therefore does not tell you whether /media inside a service or container maps to it. The service's pathname and namespace must reach the expected tree before file permissions can be interpreted.

    Likewise, adding an account to a group does not automatically update credentials of the existing server process. A supported restart can establish new process credentials, but it will not fix an incorrectly mapped path or a remote share denying the resulting identity.

    Startup timing can create a different failure

    A server may start before its network storage is ready. If the path exists as an uncovered mount-point directory, the process can see the wrong contents. If a remote mount remains present but is unreachable, operations can wait or time out.

    Making the service start later can address an ordering problem. It does not establish continuous availability after startup. The distinction between startup dependency and ongoing mount health matters for a server intended to run unattended.

    An original comparison captures the observations without using real accounts:

    Desktop: M:\Film.mkv -> mapped share; read succeeds
Service: M:\Film.mkv -> mapping absent; path lookup fails
Service: \\nas.example.test\Media\Film.mkv
         -> destination named; authentication and read checks still required

    Identify the failed operation

    For a concrete storage error, establish the server process's identity, the path as that process sees it, and the operation that fails. Enumeration, reading a film and creating a sidecar may have different outcomes.

    Testing only as an administrator can hide the relevant restriction. The useful evidence is the result under the running service's intended context. Operating-system and server logs can then distinguish path-not-found, denied access, incompatible handles and remote timeouts, each of which has a different mechanism.
