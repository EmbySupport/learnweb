    Disk spin-down, wake latency and idle workloads

    Disk spin-down stops an idle drive's platters, saving some power while adding a wake interval to a later access.

    A rotating drive can enter a standby state after inactivity. Its platters stop, and a later request must wait for the drive to become ready before normal access resumes. This is different from a whole server sleeping: the operating system can remain awake while an individual disk is stopped.

    The result can be a noticeable pause on the first film after a quiet period, followed by normal playback once the disk is running.

    The first request includes wake time

    If a fictional drive takes 7 seconds to become ready and the subsequent access takes 15 ms, that first request cannot finish in 15 ms. Its simplified duration is 7.015 seconds. Later reads avoid the wake component until the drive enters standby again.

    Read-ahead and an existing player buffer can hide some delays during continuing playback. They cannot provide uncached source bytes before the device wakes. A library entry remaining visible also does not mean its disk is currently spinning.

    What counts as idle?

    An idle policy measures activity at a particular layer. An application can read a cached file without accessing the physical disk; a background task can access the disk without any viewer starting playback.

    Activity Possible effect on the drive's idle interval
    Artwork already held in memory May require no physical disk operation
    Library scan opening uncached paths Can create storage activity
    Monitoring or health software May wake a drive, depending on the command and implementation
    Recording to that drive Continuing writes prevent an idle period
    Access through an enclosure The bridge may have a separate power policy

    For an original ten-minute idle model, an actual disk access at 09:57 moves the earliest eligibility to 10:07. A cached read at 10:03 does not reset this model's disk-activity clock. Real firmware and operating systems define their own policies.

    A repeated pause has a different explanation

    If every short interaction is slow, examine whether the drive repeatedly enters standby, whether an enclosure disconnects, or whether a storage/network request is timing out. These produce different operating-system evidence. A wake delay should be associated with a transition from an idle state; it is not a general explanation for all slow disk operations.

    There is no universal best timeout. Frequent starts and stops, response expectations and the exact drive's documented power behavior influence the choice. For an Emby server, relate the quiet periods and background workload to the first-access behavior you actually observe.
