    Media backups and recoverable generations

    Media backups retain recoverable copies of source files and related assets, with generations and failure-domain separation suited to the collection.

    A media backup preserves the source files you intend to recover: films, recordings, music, photographs and any related assets that are part of your collection. Emby's server-state backup is a different scope. Saving the server configuration does not imply that all those source files have been copied.

    The useful question is what you could recover after a particular loss, and how you would find the intended generation.

    Copies need a failure model

    Failure Property a useful recovery copy needs
    One drive fails Content available outside that failed device
    A file is accidentally overwritten A retained version from before the overwrite
    The server and attached storage are lost A copy outside that shared location
    A destructive change propagates automatically History or a copy outside that propagation path
    One backup generation is unreadable Another usable generation or a recoverable chain

    RAID can keep data available through specified member failures. It does not automatically give the overwrite-history or location independence in this table.

    Synchronization can preserve the wrong current state

    A synchronized destination can be a useful copy of the live collection. If it immediately reproduces deletions and overwrites, however, it may stop containing the earlier state you need.

    An original timeline illustrates the difference:

    Monday: live Film-A exists; recovery generation G1 contains Film-A
Tuesday: Film-A is removed from live storage
Current mirror after sync: Film-A absent
Retained G1: Film-A still present

    The mirror and G1 now answer different recovery questions. Retention is a deliberate rule about keeping generations, not a side effect guaranteed by having a second disk.

    Incremental copies have dependencies

    A full backup can be followed by incremental changes. Recovering a later point may require the base and the relevant increments in their documented order. Other systems retain complete logical snapshots while sharing unchanged storage underneath.

    A small incremental file does not establish that it can restore the entire collection by itself. Check the recovery method's dependency graph, not just the latest backup's creation date.

    Sidecar subtitles, local artwork and metadata may be valuable alongside the main media files. Their inclusion depends on where they are stored and whether they are part of your intended recovery scope.

    A readable copy should be sampled through recovery

    Checksums can verify byte agreement, while a restoration test verifies that you can locate, retrieve and use the required content. A successful copy report alone does not test every future restore operation.

    For a changing Emby collection, retained history and independent copies can be combined according to the failures that matter. The restoration process turns those storage properties into a usable collection again.
