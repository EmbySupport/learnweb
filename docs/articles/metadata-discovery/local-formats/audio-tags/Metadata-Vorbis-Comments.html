    Vorbis comments

    Vorbis comments store length-prefixed UTF-8 name/value entries with case-insensitive field names and support for repeated values, within the enclosing codec's metadata structure.

    Vorbis comments represent metadata as named UTF-8 entries. The comment structure includes a vendor string and a list of entries with explicit byte lengths.

    The vendor identifies the writing implementation's context; it is not automatically the track's artist or album.

    A field can have repeated entries

    An original example is:

    ARTIST=Ana
artist=Bo
TITLE=A=B

    ARTIST and artist identify the same field name under the format's case-insensitive ASCII name rule. The two values can describe two entries.

    The first equals sign separates name from value. In TITLE=A=B, the title value is A=B, not merely A.

    Entry UTF-8 bytes in the whole name=value entry
    ARTIST=Ana 10
    artist=Bo 9
    TITLE=A=B 9

    Lengths count bytes, not a generic character count. A non-ASCII value can occupy more UTF-8 bytes than its displayed letters suggest.

    The inner lengths have a defined byte order

    A four-byte unsigned length precedes the vendor bytes; another count describes the number of entries; each entry has its own four-byte length. These integers use the format's little-endian order.

    With vendor Demo and the three entries above, the original inner-content model occupies:

    4 + 4 + 4 + (4 + 10) + (4 + 9) + (4 + 9) = 52 bytes.

    This excludes the enclosing codec/packet framing. It is a small structural example rather than a complete encoded audio file.

    The enclosing format still matters

    Vorbis's comment header has its packet relationship and framing bit. FLAC carries a corresponding comment structure in a metadata block with its own outer rules; it does not copy every Ogg/Vorbis packet byte.

    Recognizing the same comment concepts therefore does not mean the whole files share one metadata offset or packet layout.

    Mapping preserves list and field meaning

    An Emby music reader can import supported named values into its library model. Keeping a repeated artist list separate from album-artist or performer meaning remains necessary.

    Multiple-valued fields explains why joining those names into a single string and later splitting punctuation can lose information. Supported input semantics and the library's selected representation determine the result.
