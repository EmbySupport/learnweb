    ID3v1 audio tags

    ID3v1 stores a fixed 128-byte trailing metadata record, while ID3v1.1 reuses part of its comment space for a track number.

    ID3v1 appends a small fixed-size metadata block to an audio file. Its familiar use is MP3 tagging. The reader can check the final 128 bytes for the TAG marker rather than discovering a variable-length set of frames.

    Fixed positions define the fields

    Byte offsets, inclusive Field Capacity
    0–2 TAG marker 3 bytes
    3–32 Title 30 bytes
    33–62 Artist 30 bytes
    63–92 Album 30 bytes
    93–96 Year 4 bytes
    97–126 Comment 30 bytes
    127 Genre code 1 byte

    The capacities sum to 128 including the marker. A 1000-byte toy file would place this block at byte offset 872.

    The genre byte refers to a code list; it is not a one-character genre name or a modern open list of several genres.

    A title cannot exceed its reserved space

    An original ASCII capacity example contains 31 characters:

    123456789012345678901234567890X

    Only its first 30 bytes fit the title field. Padding fills unused space for shorter values, but it cannot enlarge the field.

    Encoding interpretation also matters. The format's small legacy fields should not be assumed to provide the same Unicode signaling as ID3v2. A byte capacity and a count of user-visible characters are different quantities.

    Version 1.1 trades comment space for a track number

    ID3v1.1 uses 28 comment bytes, a zero separator byte, and the remaining byte before the genre for track information. It remains a 128-byte block.

    That is a constrained extension, not a flexible new set of arbitrary named fields. Rich credits, long descriptions and multiple values need another representation.

    Another tag can coexist with it

    A file can carry richer ID3v2 information as well as a trailing v1 record. If the two disagree, a reader's supported version and selection rules affect the displayed title.

    For Emby music, compare the actual tag records with the imported field rather than assuming the title came from the filename. ID3v2 develops the variable frame representation and its text-encoding boundary.
