    ID3v2 audio tags

    ID3v2 organizes audio metadata into identified frames with version-specific sizes, text encodings and structured payloads rather than a fixed set of trailing fields.

    ID3v2 stores identified information frames in a tag associated with audio. A frame names its kind of information and describes its own payload length and flags.

    That makes it possible to carry much more than ID3v1's fixed title/artist/album slots.

    The tag version defines how the frames are read

    A tag header identifies ID3, major/revision version, flags and body size. A frame then has an identifier, size information and flags before its payload.

    Common frame ID Role
    TIT2 Title information
    TPE1 Artist/performer information
    TALB Album information
    TRCK Track-position information
    APIC Attached picture
    COMM Structured comment

    For Emby music, retain the tag version and the frame's meaning when comparing a file with its imported title, album or artist values. Music naming provides the product context.

    Version 2.3 and 2.4 are not byte-identical contracts. For example, the tag-header size uses synchsafe encoding, but v2.3 frame sizes use ordinary big-endian integers while v2.4 frame sizes use synchsafe integers.

    Treating every four-byte size as the same integer can put the next frame boundary in the wrong place.

    Synchsafe integers reserve a bit in each byte

    A four-byte synchsafe value carries seven useful bits per byte:

    value = b0 × 2²¹ + b1 × 2¹⁴ + b2 × 2⁷ + b3.

    For 00 00 02 00, that gives 256. Interpreting those bytes as a normal big-endian integer instead gives 512.

    The version and field definition determine which interpretation applies. The bit pattern alone is not a complete size parser.

    One original title tag can be read end to end

    For a small ID3v2.4 tag carrying only the UTF-8 title Café, with no extra header, padding, unsynchronisation or footer:

    Tag header:
49 44 33 04 00 00 00 00 00 10

TIT2 frame header:
54 49 54 32 00 00 00 06 00 00

Payload:
03 43 61 66 C3 A9

    The title's UTF-8 text occupies five bytes. Its encoding byte makes a six-byte payload. Adding the ten-byte frame header makes 16 bytes of tag body, represented by 00 00 00 10. The ten-byte tag header gives 26 bytes total.

    This is an original minimal tag example. A complete reader also handles applicable flags, version rules and other frames; parsing this case is not a conformance suite.

    Not every payload is plain text

    APIC carries an image-related structure including encoding, MIME description, picture type, a description and picture data. COMM likewise has more structure than a bare string.

    Scanning the entire tag for printable characters can mix descriptions with binary bytes or lose the attached image's role. Embedded cover art develops that selection.

    Text frames can also have version-specific multiple-value conventions. A slash that a legacy application uses as a separator can occur in real wording, so blindly splitting every field changes its meaning.
