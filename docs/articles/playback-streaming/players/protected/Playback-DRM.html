    DRM-protected media and authorized playback paths

    DRM-protected playback combines encrypted media with a compatible key system, usable authorization and the required processing and output conditions.

    DRM-protected media needs more than the decoder for its video or audio codec. The receiving path must also support the applicable protection system and hold usable authorization for the encrypted samples.

    This creates another layer in playback compatibility. A codec, container and network can all work while protected presentation remains unavailable.

    Media and authorization have different roles

    Component Role
    Encoded media The compressed pictures or audio samples
    Media encryption Protects the selected media data
    Key system and decryption component Interprets protection information and manages usable keys
    License or authorization response Supplies system-specific authority and conditions for using keys
    Playback/output path Meets the required preparation and output conditions

    A key identifier is not the key itself. A media description can identify encryption or a required key without granting the receiving application permission to decrypt it.

    Browsers use Encrypted Media Extensions to connect an application to supported key systems. Native players have platform-specific protected-media integration. Neither arrangement makes every key system available everywhere.

    A positive codec result leaves another question

    Use an original four-case comparison:

    Supported encoded configuration Usable protected-playback authorization Result to investigate
    Yes Yes Continue checking the actual media and output path
    Yes No Protection-system, license or authorization readiness
    No Yes Encoded configuration or player-path compatibility
    No No Both sets of requirements remain unresolved

    The first row is not a guarantee of the complete session. It establishes two prerequisites while delivery, initialization and presentation still have their ordinary work to do.

    For an Emby media-server comparison, possessing an encrypted resource does not establish a supported path for decoding or creating another representation. Conversion requires the relevant usable input path; a server's ordinary codec support does not supply a provider's key-system authorization.

    HTTPS protects a different boundary

    HTTPS protects communication between endpoints. Media encryption can keep samples protected within the resource after it has been delivered.

    Downloading an HTTPS-served, unprotected MP4 produces ordinary usable media bytes once the permitted transfer is complete. Downloading protected sample data leaves that protection in place.

    Conversely, a failed HTTPS connection concerns resource access or transport. It does not by itself identify a DRM license failure. A useful diagnosis records the stage that produced the error.

    Key readiness can change over time

    Protected playback can require a license exchange after the application encounters initialization data. A key might be pending, usable, expired or restricted by the output context.

    The EME model exposes key-status information such as usable, expired and output-restricted. Their presence gives the app scoped evidence about protected-media readiness. A restricted output status should not be interpreted as “the codec is absent.”

    Authorization lifetime, renewal and output conditions belong to the applicable protection system and service. The details should be read from that system's supported player integration rather than inferred from the filename.

    Offline bytes and offline authorization are separate resources

    An offline protected session can require retained media and a supported persistent license. Downloading the media alone establishes only the first resource.

    Persistent authorization also does not imply that every condition has disappeared: its own system-specific lifetime and playback/output requirements still apply. EME makes persistent-license sessions optional.
