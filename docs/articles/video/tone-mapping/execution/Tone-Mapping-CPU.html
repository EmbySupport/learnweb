    CPU Tone Mapping

    CPU tone mapping carries out the brightness conversion on the computer's general-purpose processor. It is still the same kind of picture operation as GPU tone mapping; the processor doing the calculations does not define the artistic result.

    For example, FFmpeg's software tonemap filter operates on floating-point RGB values in linear light. Other processing must interpret the incoming HDR signal and prepare the final output format. The tone curve is only one step in that conversion.

    The work scales with the pictures, not just the bitrate

    A frame contains pixels to process even when its compressed file is small. These simple counts show why resolution and frame rate matter:

    Video size and rate Pixels per second, approximately
    1920 × 1080 at 24 fps 50 million
    3840 × 2160 at 24 fps 199 million
    3840 × 2160 at 60 fps 498 million

    Pixel counts only, not a performance benchmark. Color conversion, decoding, encoding, and memory traffic add their own costs.

    Four times as many pixels does not guarantee exactly four times the processing time, but it does explain why a comfortable 1080p workload says little about 4K at a higher frame rate. Multiple simultaneous sessions add to the total.

    In an Emby transcoding session, CPU use may also come from decoding, subtitle rendering, audio conversion, or encoding. A high CPU reading alone does not identify tone mapping as the bottleneck. Likewise, an accelerated encoder does not prove that all preceding filters run on the GPU.

    Software processing can be useful when the required GPU path is unavailable or when the frames are already in system memory. Moving them to a GPU and back has a cost of its own. The Emby Windows FAQ gives a concrete example of a player combining software decoding with GPU presentation.

    Compare the whole playback path, including whether it keeps up with the source frame rate. The labels CPU and GPU are execution choices, not quality ratings.
