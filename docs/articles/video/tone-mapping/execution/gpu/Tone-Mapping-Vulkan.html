    Vulkan Tone Mapping

    Vulkan gives applications explicit access to graphics and compute work on a GPU. A renderer can use that access to run shaders that convert color and compress the brightness range of HDR pictures.

    A shader is a program executed by the GPU. The tone-mapping behavior comes from that program and its parameters; Vulkan supplies the execution interface. Choosing Vulkan does not choose a particular curve or guarantee better highlight detail.

    The renderer sits above the API

    libplacebo is an example of a rendering library with a Vulkan backend. It provides picture-processing operations above the lower-level device interface. FFmpeg can use libplacebo as a video filter, showing how the same kind of GPU processing can form part of a conversion rather than only drawing directly to a screen.

    Layer What it determines
    Tone-mapping implementation The curve, peak handling, and color decisions
    Rendering library How the image-processing operations are assembled
    Vulkan driver and device The available GPU capabilities and execution of the submitted work

    This separation helps explain why two players can both use Vulkan and still look different. Their processing options, library versions, and assumptions about the display can differ.

    Vulkan support is also distinct from Vulkan Video codec support. Running tone-mapping shaders does not require that decoding use Vulkan Video; frames can originate from another decoder when the application supports the necessary transfer or sharing. Those connections have their own format and synchronization requirements.

    In an Emby discussion, first identify whether processing occurs on the server or in the player. A Vulkan-related renderer setting or message concerns that particular application's path. It does not establish that a separate server transcode uses the same API. Availability and performance depend on the complete implementation and driver, not merely a Vulkan version listed for the graphics card.
